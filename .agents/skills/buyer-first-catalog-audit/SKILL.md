# Buyer-first Catalog Audit

Перед действиями прочитай `docs/ai/CATALOG_SWARM_MASTER_PROMPT.md` **полностью** и `docs/PRODUCT_PRINCIPLE_BUYER_FIRST.md`. Это обязательные инструкции workflow.

## Запуск

1. Проверь актуальную `main`, открытые PR и реестр каталога, не перезаписывай существующую работу.
2. Раздели товарные группы между независимыми потоками и выдай каждому критерии, формат записи результата и ссылки на исходники из мастер-промпта.
3. Применяй конкурентные источники только как подтверждение рыночной терминологии и примеров, а не нашего склада. ГОСТы/марки проверяй отдельно.
4. Для каждой карточки сформируй первые 3–5 параметров + марки/исполнение + ГОСТ + прямой запрос, полную таблицу оставь ниже.
5. При подготовке изменений обеспечь ветку/PR, ревью, preview READY, затем production READY. Технически спорные изменения без ревью не публикуй.
6. Сдавай конкретный результат: URL, подтверждённые примеры, ссылки-источники, PR, QA, остающиеся риски.

Если параллельных агентов недоступно, используй отдельные задачи GitHub по группам и двигайся в ограничениях доступных инструментов. Не представляй созданные задачи как уже выполнившихся агентов.

## Постоянные критерии

- Никаких вымышленных комбинаций «размер × марка × ГОСТ × наличие».
- Не смешивай Дн, DN и PN; марки сплавов и классы прочности; номинальный ряд и подтверждённый склад.
- Нет обязательной корзины: готовую спецификацию можно отправить без поиска.
- По всем товарным URL — проверка мобильного UX и корректной заявки.

## Проверки качества карточек по утверждённому варианту А (04.11.2026)

При работе с каталогом применять и `.agents/skills/typography-scale/SKILL.md`. Скилл не дублирует `skills/metal-directory-auditor` (технические данные) и `qa/README.md` (общий QA): это один чек-лист приёмки для покупателя.

**Текстовая целостность на 320, 390, 1536 px и 200%:**
- Товарное название и CTA не обрезаны; выбор размера не перекрывает заявку, горизонтальной прокрутки нет.
- `Марки — материал`, перечень обозначений, пояснение стандарта, caution (например, о литых/деформируемых бронзах) и `Источник стандарта` отделены друг от друга; ни одной строки вида `М1М2М3`.
- В `TechnicalCatalogSummary` все `span` и ссылки имеют читаемый визуальный разделитель или сеточный gap; не полагаться на JSX-пробелы между тегами.
- Каждая марка, для которой есть страница в `src/data/materials.ts`, ведёт на её действительный slug; неизвестная марка остаётся обычным текстом, без подставной ссылки на группу. Проверка `material-page-links.int.spec.ts`.
- Пояснения, подписи форм, размеры, ГОСТ, дисклеймеры и ссылки отделены, не перенесены поверх других элементов; шрифт и touch-target соответствуют действующим типографическим тестам.
- Нормативный ряд не приравнивается к наличию; комбинации марки/размера/ГОСТ и цены не выводятся из отсутствующих данных.

**Проверка продаж и ссылок:**
- От обозначения ГОСТ можно перейти к существующей странице справочника либо виден честный простой текст.
- Выбранный размер передаётся в `/?product=...#request`, заявка допускает неполную/нестандартную спецификацию; реальный тестовый лид не отправлять.
- Кнопки и ссылки получают разборчивые подписи, находятся рядом с товарным параметром, не создают ложный «В наличии».

**Визуальная приёмка:**
- Сравнить реальную отрисовку с **утверждённым изображением варианта А**, а не только с CSS или описанием. Эталонное изображение хранить в разрешённом рабочем контексте; без него статус «пиксельное совпадение» недопустим.
- Снимать образцы: цветные металлы (бронза, медь), нержавейка, трубная карточка, фасонный прокат и СДТ; автоматические тесты не заменяют просмотр скриншотов.
- Если сторонний тест падает на пограничном допуске (например, touch-target 43.9999 против 44 px), зафиксировать и исправить реальное поведение/устойчивость теста до публикации, не игнорировать job.

**Состояния задач:** `TODO → IN_PROGRESS → VERIFIED → DEPLOYED` либо `BLOCKED` с причиной. Для каждой фиксировать URL, источник, PR, тесты, production commit SHA и остающиеся несоответствия. Запись в Obsidian проверять фактическим чтением файла; автоматический двусторонний sync нельзя считать работающим без подтверждения.

**План проекта:** действующий список приоритетов `2026-11-04 - Сайт и Magic Metal OS - сверенный план` в Obsidian. Более старые сентябрьские сведения о branch/main и проблемах webhook, Customer Experience или интеграций — гипотезы до повторной проверки на актуальном checkout.
