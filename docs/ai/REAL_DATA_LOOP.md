# MAGIC METAL — REAL DATA LOOP

> Это не новая фаза. Это рабочий контур после базового цикла проекта.

## Принцип

Разработка продолжается только от фактических данных и конкретной бизнес-проблемы:

`каталог → заявка → закупка → КП → сделка → фактический результат → знание → следующая заявка`

## Фактический результат

Для каждой завершённой заявки внутренне фиксируются:

- выиграна / проиграна / отменена;
- причина проигрыша или отмены;
- сумма КП;
- фактическая сумма продажи;
- фактическая закупочная стоимость;
- фактическая логистика;
- фактическая себестоимость;
- фактическая валовая прибыль;
- фактический срок поставки;
- успешность поставки;
- рекламация и комментарий;
- фактический маршрут закупки;
- фактический источник закупки;
- дата фиксации результата.

## Ограничение клиента

Все фактические закупочные данные являются внутренними. Они не попадают в публичный каталог, клиентское КП или публичные API.

## Правило следующей итерации

Не создавать новую крупную функцию только потому, что она возможна.

Сначала определить проблему по реальным данным, затем сделать минимальное изменение, проверить его и зафиксировать результат:

`проблема → гипотеза → одно изменение → измерение → решение`

## Первый приоритет после внедрения

1. Получить production-green.
2. Накопить реальные RFQ и результаты сделок.
3. Найти первую измеримую потерю или ошибку.
4. Исправить только её.

## Запрещено без доказанной необходимости

- отдельный BI;
- ML для ranking;
- новая CRM;
- сложная A/B-платформа;
- автономное изменение закупочной политики;
- расширение Procurement Engine без реального кейса.
