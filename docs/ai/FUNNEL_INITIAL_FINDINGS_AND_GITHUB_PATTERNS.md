# Первый вывод по воронке и проверка аналогов (02.11.2026)

## Что доказано, что является гипотезой
1. **Доказано по коду:** обе реализации формы до этого PR могли считать HTTP 2xx успешным отображением даже без подтверждения доставки/записи; при этом событие `request_sent` не отправлялось. Исправлено в обоих вариантах; требуется профильный CI/QA. Это не доказательство фактической потери лидов.
2. **Доказано по коду:** события `catalog_product_opened`, `size_selected`, `request_started`, `request_sent` предусмотрены. Фактические конверсии неизвестны.
3. **Гипотеза UX:** разделение марки, размеров и CTA, а также обязательность знания ГОСТ способны снижать заявки; проверять на конкретных сценариях и в сопоставимых визитах.
4. **Гипотеза продаж:** отказы могут возникать и после заявки: доставка письма, ответ менеджера, КП, цена/логистика, сделка. Нужны обезличенные стадии из CRM/учёта.

## Историческое ограничение
Документ `docs/ai/CONTINUE_METRIKA_CATALOG_2026-10-17.md` описывает отчёт за 17.10 (5 визитов, 5 посетителей, 33 просмотра, 0 новых целей) **без повторного подтверждения API**. Этого объёма недостаточно для выводов о поведении или коммерческом эффекте. Новых фактических отчётов в этом исследовании нет.

## Какие архитектуры применять
- PostHog: https://github.com/PostHog/posthog — событийная аналитика, funnels/path analysis, продуктовые гипотезы. Принцип: фиксировать этапы по одной когорте и искать выпадения, не сравнивать просто число кликов с числом посетителей.
- GrowthBook: https://github.com/growthbook/growthbook — контролируемые эксперименты и фичефлаги. Принцип: изменения маленькими партиями и обратимый rollout; новый сервис не внедрять без необходимости.
- OpenTelemetry: https://github.com/open-telemetry/opentelemetry-js — наблюдаемость технических ошибок и задержек. Принцип: отличать ошибки транспорта и сервера от ухода покупателя; не передавать контакты/содержимое заявок.
- RudderStack: https://github.com/rudderlabs/rudder-server — событийная маршрутизация. Для нашего масштаба пока избыточно: оставляем текущие 11 целей Метрики.

## Ближайшее решение
Сначала профильный тест: HTTP 200 с `ok:true`, но без `id` и флагов `emailDelivered`/`crmDelivered` должен **не** сбрасывать форму и показывать честное сообщение. После CI — живые показатели Метрики (без новых счётчиков) и сопоставление с реальными ответами/КП менеджера. Не отправлять реальную тестовую заявку.
