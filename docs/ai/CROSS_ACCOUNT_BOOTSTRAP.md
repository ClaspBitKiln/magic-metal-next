# MagicMetal — запуск с нового ИИ-аккаунта через предоставленный доступ

## Суть

**Доступ к GitHub = право прочесть рабочую архитектуру, получить код и запустить проверки.** Доступ не равен автоматическому подключению всех сервисов и не позволяет передавать секреты одного аккаунта другому. Реализованное: единый каталог документации и автоматическая проверка push/PR в GitHub Actions. Не реализованное: автоматическое обнаружение самого входа в новый ChatGPT/Claude/Gemini аккаунт.

## Однотипная процедура нового аккаунта

1. Владелец добавляет GitHub-пользователя в `ClaspBitKiln/magic-metal-next` с минимальными правами; новый пользователь принимает приглашение. Для GitHub connector нового AI-аккаунта пользователь отдельно разрешает доступ к этому репозиторию.
2. ИИ-агент с доступом первым делом читает `docs/ai/CROSS_ACCOUNT_BOOTSTRAP.md`, `docs/ai/PROJECT_SYSTEM_ARCHITECTURE.md`, `AGENTS.md`, `MEMORY.md`, `docs/ai/AI_SITE_WORKFLOW.md`. Он не должен угадывать пути или состояние.
3. Новый аккаунт фиксирует HEAD SHA `main`, активные PR, `git status`, затем работает только в своей ветке `feat/<topic>-<date>` или `review/<topic>-<date>`. Стандартный цикл: commit → push → PR → GitHub Actions → Vercel preview → approval → merge.
4. В GitHub Actions включён файл `.github/workflows/site1-cross-account-validation.yml`, который запускается автоматически при push в `review/**`, `feat/**`, `fix/**` и на PR с кодом/тестами. Проверяет lint и интеграционные тесты. Для доступности кнопки ручного запуска требуется наличие workflow в default branch.
5. Передача секретов только через GitHub Actions secrets и Vercel environment variables в зависимости от сервиса. Никаких личных токенов в issue, PR или коде.
6. Обсидиан: локальная Windows Scheduled Task `MagicMetal Catalog Sync` поддерживает GitHub → локальный vault на конкретном устройстве. **Доступ к репозиторию не выдаёт доступ к Windows**, и эта задача автоматически не появляется у других аккаунтов.

## Что нужно для буквально автоматического запуска при входе в аккаунт

Надёжное решение: *авторизованный GitHub App / OAuth gateway*, связанный с системой, в которой пользователь действительно входит:

- только проверенный OIDC/OAuth login callback (state, PKCE, nonce, проверенный user ID);
- после согласия проверка прав пользователя на конкретный GitHub repo через GitHub App;
- ограниченный webhook/repository_dispatch либо workflow_dispatch от сервиса доверия (не из произвольного браузера и не с общим PAT);
- идемпотентность: один bootstrap на новую GitHub-идентичность/версию конфигурации; повторный логин не разрушает данные;
- GitHub Actions создаёт отчёт/проверки, а не выдаёт токены и не начинает production deploy;
- изоляция аккаунтов: персональные секреты, браузерные профили и разрешения отдельны. Для Vercel, Windows, Obsidian и CRM нужны отдельные разрешения.

Без фактического OAuth callback от провайдера входа **невозможно честно заявить, что запуск произойдёт автоматически при каждом входе в любой ИИ-аккаунт**. Если AI-платформа не предоставляет такой callback, ближайший безопасный вариант — one-click авторизация GitHub App с автоматическим событием после подтверждения доступа.

## Быстрые команды в новом checkout

```bash
git clone https://github.com/ClaspBitKiln/magic-metal-next.git
cd magic-metal-next
npm ci
npm run dev
# для тестов:
npm run lint
npm run test:int
```

Реальные переменные берутся из защищённого окружения. Публичный шаблон: `.env.example`. Для локальной базы: `docker compose up -d postgres` **только** если это отдельная тестовая БД; не использовать production DATABASE_URL в локальном окружении.

## Обязательные ограничения

Запрещены `reset --hard` чужой рабочей копии, `git push --force`, слепой merge и запуск реальных клиентских заявок агентами. Любой статус «готово» подтверждать SHA/PR и логами тестов. Разрешения на аккаунты и окружения не передавать автоматически по одной только ссылке на GitHub.
