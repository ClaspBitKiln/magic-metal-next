# MAGIC METAL — MASTER PLAN

> Единый рабочий план проекта. Выполнять строго по этапам сверху вниз. После завершения каждого этапа: проверить результат, зафиксировать изменения в GitHub, обновить статус и только затем переходить дальше.

## 0. НЕИЗМЕНЯЕМЫЕ ПРИНЦИПЫ

1. Публичный каталог единый: клиент не выбирает поставщика и не видит внутренние источники.
2. Публикуем только позиции, для которых существует реальный и проверяемый маршрут закупки.
3. Внутренние слои поставщиков, цены закупки, маржа, источники и ранжирование скрыты от клиента.
4. Базовый справочник — прайс/номенклатура Металлсервис как отдельный внутренний слой ходовых позиций.
5. Все поставщики/заводы — отдельные внутренние слои данных, без переключателя для клиента.
6. Наличие клиента: `На складе` / `Наличие уточняется` / `Под заказ`.
7. SDT — обычная категория единого каталога.
8. Размеры и практическая номенклатура сопоставляются с ГОСТ и рыночными размерами, но справочные позиции без закупочного маршрута не становятся продаваемыми.
9. Выбор поставщика делается по полной себестоимости поставки (landed cost), а не только по цене материала.
10. Реальные источники важнее красивой витрины: никаких фиктивных цен, наличия, API или поставщиков.
11. Все секреты только в локальном окружении/секрет-хранилище; в GitHub их не помещать.
12. Obsidian — постоянная база проектных знаний; GitHub — технический source of truth и резерв.

# ФАЗА 4 — PROCUREMENT ENGINE MVP

### Цель
Автоматически определить, где реально купить товар и какой маршрут выгоднее.

### Pipeline
`RFQ → normalize → discover → verify → compare → landed cost → benchmark → rank → approve → quote → learn`

### Реализовать
- Offer;
- Source;
- Supplier;
- Manufacturer;
- Benchmark;
- Procurement Decision;
- состояния RFQ;
- deterministic matching;
- configurable ranking;
- explainable decision;
- `no_procurement_route`, если реального маршрута нет.

### Ranking
Учитывать настраиваемые веса: landed cost, соответствие спецификации, наличие, срок, надежность, логистика, документы, benchmark.

### Результат
Внутренняя система отвечает: что покупать, у кого, откуда, каким маршрутом и почему.

# ФАЗА 6 — ПОДКЛЮЧЕНИЕ ИСТОЧНИКОВ И MCP/PLUGINS

### Цель
Перевести реестр из ручного справочника в рабочую систему данных.

### Правило
Не предполагать наличие API. Для каждого источника сначала проверить официальный механизм доступа.

### Приоритет интеграций
1. Официальный API / feed / commercial portal.
2. Официальный экспорт / price list / structured data.
3. Разрешенный connector/MCP.
4. Автоматизированный browser workflow там, где это допустимо.
5. Ручной RFQ — как fallback.

### MCP / Plugins
Использовать доступные MCP/плагины там, где они реально сокращают ручной труд:
- GitHub — код, документы, CI, source of truth;
- Firecrawl — исследование и получение публичных страниц/структурированных данных там, где это уместно;
- Notion/другие workspace connectors — только если нужны конкретные рабочие данные;
- Obsidian MCP — база знаний и синхронизация проекта;
- TRIGGERcmd — локальные Windows-операции только через реально доступные команды;
- OpenAI Platform — только для необходимых API/AI-интеграций, без хранения ключей в репозитории.

### Результат
Каждый источник имеет конкретный `integration_method` и `integration_status`; никаких фиктивных интеграций.
