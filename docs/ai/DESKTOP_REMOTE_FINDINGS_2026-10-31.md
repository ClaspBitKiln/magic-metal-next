# Desktop Commander: найденные варианты диагностики — 31 октября 2026

В текущем чате инструменты Desktop Commander отсутствуют. Подключение аккаунта
подтверждено скриншотом пользователя; последнее показанное состояние устройства
было Offline. После перезапуска пользователь передал лог: локальный MCP
подключён. На следующем скриншоте после Connecting to Remote MCP запрос
завершился `Device startup failed: fetch failed`, затем устройство остановилось.
Это подтверждает сетевой сбой Node при обращении к remote endpoint, но не его
причину (DNS, соединение, proxy или TLS). Успешный remote/channel/presence
handshake из этой сессии не подтверждён.

Изучены текущая официальная документация и публичные GitHub issues:

- [Официальная инструкция](https://github.com/wonderwhy-er/DesktopCommanderMCP/blob/main/src/remote-device/README.md):
  локальный процесс Remote и AI connector — отдельные части. Штатный перезапуск
  переиспользует сохранённую сессию. Удаление сессии/отзыв устройства не являются
  первым шагом исправления.
- [#811](https://github.com/wonderwhy-er/DesktopCommanderMCP/issues/811): пользователи
  описали `IncreaseConnectionPool`, отказ канала и последующее самостоятельное
  восстановление. В обсуждении предложено сохранять один запущенный экземпляр,
  не создавать циклы перерегистрации. Именно этой ошибки в нашем логе нет;
  назначать её причиной без нового лога нельзя.
- [#798](https://github.com/wonderwhy-er/DesktopCommanderMCP/issues/798): сообщалось
  о расхождении Online панели и Offline в диспетчеризации MCP. Наш последний
  скриншот показывает Offline; совпадение симптома не установлено.
- [#891](https://github.com/wonderwhy-er/DesktopCommanderMCP/issues/891): сообщалось
  об изменении схемы инструментов при нескольких аккаунтах. Воспроизведение
  использовало `who_am_i` с выбранной привязкой, затем точные link/device selectors.
  В текущей сессии нет даже `who_am_i`; выполнить этот workaround нельзя.
  Чужие идентификаторы из issue не переносить в нашу конфигурацию.

Вывод: ранее работающий Remote может перестать работать без изменения настроек
ПК. Текущую причину это не доказывает. Нужно независимо подтвердить достижение
Online устройством и передачу инструментов текущему чату. Облачная программа
не может выдать чату отсутствующую capability или подключить приложение к аккаунту.
Перезапуск Remote в облаке зарегистрирует облачную машину, а не Windows пользователя.

Скрипты восстановления из GitHub восстановлены в `scripts/`; на ПК из текущего
чата не запускались. Диагностика текущей среды —
`/workspace/connection-diagnostics/desktop-report.json`, секреты не читались.
Для Windows подготовлен архив `/workspace/connection-diagnostics/DesktopCommander-Network-Check.zip`:
получает вложенные коды ошибки Node fetch, проверяет IPv4-first и системные CA
только как локальные параметры процесса. TLS-проверка сохраняется. При успехе
варианта создаёт launcher с проверенной опцией; ключи и saved sessions не читает.
На Windows из этой сессии не запускался — удалённого управления пока нет.
