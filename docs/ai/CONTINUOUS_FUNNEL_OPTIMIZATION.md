# Непрерывное улучшение воронки продаж — «Сайт2»

**Цель:** не бесконечно переделывать каталог, а регулярно улучшать результат: больше целевых заявок от закупщиков Сибири, Дальнего Востока, Севера и СНГ при том же или меньшем усилии покупателя.

## Разделение стабильного и изменяемого
- **Каталог**: один раз проверяем размер, марку, ГОСТ/ТУ, исполнение и взаимосвязи, утверждаем базовую версию. Меняем только при выявленной ошибке, изменении норматива или доказанной проблеме удобства.
- **Воронка**: постоянно анализируем и улучшаем пути от поиска до заявки, но только по данным; одна гипотеза → ограниченное изменение → измерение → оставить/откатить.
- **Рой**: независимые роли для анализа трафика, поведения, UX, качества заявок и экспериментов. Агенты не должны заменять анализ и не должны создавать постоянную нагрузку без полезного решения.

## Что уже измеряется
Счётчик Яндекс Метрики **113661397**; события из `public/analytics.js`:
`catalog_product_opened`, `standard_opened`, `size_filter_used`, `size_selected`, `request_click`, `request_started`, `specification_attached`, `request_sent`, `request_error`, `phone_click`, `email_click`.
Значения формы и файлы в аналитику не передавать. По коду события возможны, но **фактические числа и полнота доставки событий пока не проверены через API Метрики**. Повторно не создавать счётчик или цели.

## Рой аналитики (запуск только при доступных данных)
1. **Источники и география**: поисковые запросы и каналы, целевые регионы, мобильные/десктопные устройства. Нет данных о закупщике — не выдумывать сегмент.
2. **Каталог → выбор**: просмотр карточки, использование фильтров и размеров, переход в заявку. Разделять посетителей и события; не строить грубые коэффициенты из несопоставимых баз.
3. **Заявка → отправка**: request_click → request_started → specification_attached → request_sent/request_error. Сверить реализацию и фактическую доставку целей. Не считать клик отправленной заявкой.
4. **Качество лидов**: число подтверждённых заявок, наличие контакта, регион, требуемая продукция, этап обработки, ответ менеджера. Работать только с разрешёнными обезличенными/агрегированными данными; не отправлять персональные данные в LLM/сторонние сервисы.
5. **UX и эксперименты**: искать конкретный провал, предложить минимальное изменение и критерии успеха; оформлять PR/preview с откатом.
6. **Независимый критик**: проверяет статистическую достаточность, сезонность, проблемы трекинга, ошибки интерпретации и цену вмешательства.

## Воронка и гипотезы
| Этап | Вопрос | Диагноз только после проверки |
| --- | --- | --- |
| Вход на товарную страницу | Переходят ли целевые посетители к размерам? | Проблема посадочной или качества трафика |
| Выбор размера / марки | Переходят ли к заявке? | Непонятные параметры, CTA не рядом, не тот ассортимент |
| Начало заявки | Почему не заканчивают? | Слишком много полей, неудобный файл, мобильный UX |
| Отправка | Есть ли ошибки? | Валидация, сеть, сервер |
| Передача менеджеру | Есть ли ответ и сделка? | Потеря лида после формы, скорость обработки |

## Один цикл улучшения
1. Проверить актуальные данные Метрики за сопоставимый период и количество подтверждённых заявок. Если API не подключён — зафиксировать блокер, не притворяться, что получена статистика.
2. Выбрать **одну** точку потерь с максимальным ожидаемым эффектом.
3. Оформить гипотезу: проблема, метрика, сегмент, минимальная правка, ожидаемый эффект и критерий отката.
4. Внести правку в отдельной ветке; проверить CI, доступность, мобильный размер и заявку с моками. Реальные тестовые заявки только после отдельного разрешения.
5. Оценить по достаточным данным, оставить или откатить. Не менять параллельно несколько элементов одной воронки так, чтобы нельзя было определить причину результата.

## Решение о частоте
Можно регулярно **проверять показатели воронки**, например раз в неделю, когда есть надёжный доступ к отчётам; не нужно регулярно собирать неизменённые разделы каталога. Настройка scheduled workflow и внешнего доступа требует отдельной проверки. Запись этого плана **не означает**, что мониторинг или REA-рой реально запущены.

## Технический приоритет
Первый этап: проверить полноту событий, в том числе передачу request_started/request_sent и связывание с реальными успешными заявками. Затем — проверить конверсии по регионам и товарам. Счётчик не создавать заново; OAuth-токены и персональные данные не помещать в GitHub.

## Обязательное правило: воронка продаж — единая система

Рассматривай всю цепочку как взаимосвязанную систему: **привлечение целевой аудитории → вход на сайт → поиск товара → проверка характеристик → выбор размера и марки → заявка/звонок/спецификация → получение и обработка заявки → предложение → сделка → повторный заказ**.

**Постоянно ищи и последовательно устраняй неоптимальности всей системы**, а не оптимизируй отдельные страницы ради красивых показателей. Применяй теорию ограничений и ТРИЗ: находи текущее главное узкое место, устанавливай причину по фактам, предлагай минимальное исправление, проверяй результат и переходи к следующему ограничению. Не создавать дополнительную работу для покупателя или менеджера.

Порядок одного цикла:
1. Картировать этапы, реальные переходы и потери; неизвестное обозначать неизвестным.
2. Выбрать самое существенное ограничение по вероятному влиянию на **качественные заявки и оплаченные заказы**, не только клики.
3. Сформулировать причину, гипотезу, метрику до/после, стоимость изменения и критерий отката.
4. Внести минимальную безопасную правку в отдельной ветке, проверить мобильность, доступность, форму, передачи данных.
5. Сопоставить результат на достаточном объёме данных; закрепить улучшение или откатить. Повторить цикл без «вечного редизайна».

Качество важнее количества: учитывать географию (Сибирь, Дальний Восток, Север и СНГ), соответствие потребности покупателя, ошибки формы, отсутствие ответа менеджера, скорость обработки, конверсию в предложение, оплату и повторный заказ. Не подменять коммерческий результат посещаемостью.

**Утверждённый каталог не мониторить и не переписывать постоянно.** Он стабильная техническая база; изменять только подтверждённые ошибки, новые требования или доказанные препятствия воронки. Рой использовать для параллельной диагностики, проверок гипотез и QA с единым владельцем результата; не плодить инструменты и отчёты ради самого процесса.

Без доступа к Яндекс Метрике, CRM и фактическим продажам не заявлять количественные потери и «победы». Не создавать новые счётчики/цели без проверки существующих. Не отправлять реальные заявки без отдельного безопасного тестового сценария. Главная цель — систематический измеряемый рост результата при сокращении трения.
