## Минимальная схема на VDS

`HTTPS80/443 → reverse proxy → Node22 на127.0.0.1:3000 → внешний SMTP`

Node — отдельный непривилегированный пользователь, запуск через systemd с явным
путём к Node/рабочей директории и защищённым EnvironmentFile. Порт3000 не открывать
как второй публичный вход. Версии приложения хранить по release-SHA; `current`
переключать после проверки, предыдущий release сохранять для отката.

Reverse proxy должен передавать Host и протокол, поддерживать обычные Next/RSC
ответы и не обрезать отправку формы. В приложении лимит тела4500000байт,
суммарных вложений4МиБ; например, proxy-лимит5МиБ должен пропускать допустимый
multipart, а прикладной лимит остаётся прежним. Таймаут proxy надо согласовать
с SMTP-таймаутами до20секунд, дополнительным webhook до8секунд и возможной записью
в БД; не ставить более короткий таймаут без проверки.

В коде IP берётся из первого `x-forwarded-for`. На единственном прямом Nginx-входе
необходимо задавать этот заголовок из доверенного адреса соединения, а не оставлять
пользователю возможность подставить первый IP. In-memory ограничение5 обращений
за15минут не является общей защитой кластера: при нескольких Node-процессах его
состояние раздельно. Для первой проверки достаточно одной контролируемой копии;
эквивалентность нагрузки/защиты Vercel ещё не измерена.

## Окружение: только имена, без значений

| Назначение | Переменные и условие |
|---|---|
| Публичные адреса/SEO | `NEXT_PUBLIC_SITE_URL=https://magicmet.ru`; технический домен не должен стать публичным canonical/sitemap |
| Метрика | `NEXT_PUBLIC_YANDEX_METRIKA_ID` либо существующий default113661397; это build-time настройка, смена требует новой сборки |
| SMTP заявки | `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `REQUEST_TO_EMAIL` |
| Payload/хранение | `PAYLOAD_SECRET`, `DATABASE_URL` — конфигурация требует их для полного runtime Payload |
| Необязательный существующий webhook | `N8N_WEBHOOK_URL` или `CRM_WEBHOOK_URL`, при используемой подписи `N8N_WEBHOOK_SECRET` |
| Сборка | `SIMPLE_PUBLIC_SITE_BUILD`, `BUILD_MEMORY_MB`; реальные настройки сверить с выбранным production-release |

Нельзя копировать секреты в отчёт, Git, публичную сборку или команды shell.
Нужен защищённый перенос фактически используемых production-значений, а не
подстановка build-only defaults. Публичный build-скрипт допускает фиктивный
локальный DATABASE_URL и build-only PAYLOAD_SECRET только для компиляции; это
**не рабочие данные БД и не production-секрет**. Он также может игнорировать
ошибки типов отложенных модулей через `SIMPLE_PUBLIC_SITE_BUILD=1`; успешная
публичная сборка не доказывает готовность CMS/закупочного движка.

Новые API-ключи поставщиков, BicoTender, OpenAI/агентов и ATI для переноса
публичного сайта не требуются. Их нельзя включать «для полноты» — эти задачи
остаются на паузе.

## Заявки, БД и файлы

`/api/request` сначала пытается записать данные/вложения в Payload, затем
отправляет SMTP и при настройке — webhook. Ошибка записи в Payload перехватывается;
это позволяет SMTP-доставке работать отдельно, но не гарантирует сохранение в БД.
Для запроса с файлами успешный SMTP обязателен: webhook передаёт метаданные/ID,
а не сами вложения. При неподтверждённой доставке менеджеру API возвращает503.

Поэтому миграционная приёмка должна проверять **получение письма и правильного
вложения**, а не только HTTP200/красивую страницу. Существующий SMTP-канал требуется
сохранить; Mail MCP Яндекса не заменяет SMTP сайта и не отправляет эти письма.
Публичный порт отправки465/587 и реальные DNS/TLS соединения SMTP с VDS проверить
до переключения домена. Никаких реальных тестовых заявок этот read-only этап
не отправлял.

В `Media`/`RequestFiles` не обнаружен адаптер Vercel Blob/S3: заданы Payload-upload
коллекции. Если CMS/запись файлов реально используются в production, перед
переносом выяснить их фактические upload-пути и обеспечить персистентный каталог
вне заменяемого release + резерв БД/файлов. Конкретный путь нельзя выдумывать.
Если CMS ещё не введена, перенос сайта не должен самовольно её вводить или
переносить пустую БД вместо существующих данных.

## Что зависит от Vercel

- Публичные обработчики используют стандартный Next/Node и Nodemailer; прямого
  импорта `@vercel/*` в просмотренном runtime-коде не найдено.
- CDN, TLS, deployment protection, edge-фильтрация и управление процессами Vercel
  не появятся на VDS автоматически. Их замену проверять на новой площадке.
- `Cache-Control:s-maxage` имеет смысл на промежуточном CDN; он не означает,
  что простой Nginx автоматически даёт тот же кэш. Не кэшировать POST/ответы
  заявок и не добавлять общий HTML-кэш без учёта RSC/locale/headers.
- `vercel.json` содержит старый cron `/api/cron/ati-logistics` (`30 6 * * *`).
  Вне Vercel этот файл не создаёт расписание. **Новый cron на VDS не создавать**:
  владелец запретил новые расписания, ATI/поставщики на паузе. Имена `CRON_SECRET`
  и `ATI_API_TOKEN` относятся к отложенному endpoint, не к обязательному запуску сайта.
- Существующая проверка доступности раз6часов находится в GitHub Actions и
  использует домен; не дублировать её новым таймером. Её наличие в коде не
  подтверждает текущую активность GitHub workflow — здесь API Actions не проверялся.

## CI-сборка вместо сборки на малом VDS

Технически допустима схема LinuxCI(Node22, x86-64/glibc целевого сервера) →
release-артефакт → обычный `next start` на VDS. В проекте уже есть CI-пример
Node22 + npmci + npmrunbuild + локальный npmstart, но готового проверенного
deployment-job SpaceWeb не обнаружено.

Для первого варианта артефакт включает свежую `.next`, `public`, package/lock,
необходимые Next/runtime-конфиги и совместимые runtime-зависимости. `sharp` и
другие нативные пакеты должны соответствовать ОС/архитектуре/Node. Не копировать
Windows node_modules и не считать старую `.next` подходящей. Исключить .env,
приватные прайсы, логи и тестовые секреты из артефакта. Удаление dev-зависимостей
и точный состав runtime подтвердить пробным запуском; здесь это не тестировалось.

**Dockerfile сейчас не готов к применению:** он копирует `.next/standalone` и
запускает `server.js`, но `output:'standalone'` в next.config.ts не включён.
Сам факт наличия Dockerfile не даёт рабочего контейнера. Возможны два отдельных
следующих решения: обычный nextstart без изменения режима сборки либо изолированная
правка standalone и профильная проверка. В этом этапе ни одно не применялось.

2ГБ RAM можно рассматривать только как гипотезу для runtime со сборкой вCI;
сборочный скрипт запрашивает heap4096МБ по умолчанию. Для4ГБ тоже нет измеренного
запаса/нагрузочного доказательства. Тариф выбирать после контрольной сборки и
измерения RSS/пиков/диска на техническом стенде, а не по общей рекламе Node-VDS.

## Приёмка до DNS

Один проверенный проход на отдельном техническом домене/защищённом стенде:

1. Главная, logo/hero/CSS/JS, sitemap.xml/robots.txt; canonical должен оставаться
   production-доменом, технический стенд не индексировать отдельным дублем.
2. `/produkciya/listovoy-prokat/goryachekatanyj`,
   `/produkciya/sortovoy-i-fasonny-prokat/krug-i-kvadrat`,
   `/produkciya/truby-besshovnye/goryachedeformirovannye`,
   `/produkciya/sdt/otvody-besshovnye`, медь/бронза и действующие ссылки справочника.
3. Языковой переход и параметры товара → предзаполненная форма без потери
   марки/размера; поиск `/api/catalog-search` с известным обозначением.
4. Пустой контакт/нет согласия/неверный файл блокируются; допустимая заявка без
   файла и с небольшим валидным PDF проходит через выбранный тестовый канал,
   письмо и вложение реально доступны. Убедиться, что ошибка SMTP даёт503,
   а интерфейс не показывает ложный успех.
5. TLS, www→apex, старые redirects, реальные IP заproxy, bodylimit и таймауты.
6. Метрика113661397, сохранение source/medium/campaign, исключение владельца
   в проверяемом браузере. При QA не отправлять реальные reachGoal/визиты и
   письма без соответствующего согласованного тестового сценария.
7. После стенда — резерв release/данных и снимок webDNS. Переключать только
   web-записи, не MX/SPF/DKIM/DMARC. Проверить итоговый домен извне и канал заявок.
8. Сохранить Vercel для отката до подтверждения нового сайта. Старые сентябрьские
   IP/DNS из архива не использовать как текущие целевые записи без новой проверки.

## Блокеры готовности

Текущий тариф/доступ SpaceWeb и наличие VDS неизвестны; productionSHA и реальный
набор env ещё не сверены; сборка/контейнер/SMTP/сохранность файлов/нагрузка на
целевом VDS не проверены. Поэтому статус — **технический план готов, перенос не
готов к переключению**. Следующее действие родителя: проверить кабинет/ресурсы,
затем подготовить независимый стенд на согласованной конфигурации.
