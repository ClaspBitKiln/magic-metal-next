# Проверка архитектур воронок на GitHub — 02.11.2026

Проверены публичные актуальные репозитории и README через GitHub API:
- https://github.com/PostHog/posthog — объединённый контекст продуктовой аналитики: события, ошибки, записи поведения и бизнес-данные. Для нашего сайта заимствуем **модель последовательных событий и сегментации**, не разворачиваем платформу.
- https://github.com/growthbook/growthbook — открытая система feature flags и продуктовых экспериментов. Для нас принцип: **гипотеза → ограниченное изменение → метрика → решение/откат**, без нового сервера и SDK на текущем этапе.
- https://github.com/open-telemetry/opentelemetry-js — инструментирование технических событий, задержек и ошибок. Для нас принцип: различать технический отказ заявки и добровольный выход; отдельный observability-stack сейчас не нужен.
- https://github.com/rudderlabs/rudder-server — событийный pipeline. Это усложнение для текущего масштаба, не внедрять, пока не появятся несколько независимых систем-потребителей.

## Текущее положение
Яндекс Метрика уже подключалась успешно 31.10, что подтверждено `docs/ai/METRIKA_CONNECTED_2026-10-31.md`. Там описаны 12 целей (11 ручных + 1 автоцель), несемплированный отчёт и явное смещение мобильного трафика роботами. Ничего не создавать заново.

Новый отчёт в `scripts/metrika-report.mjs` (этот PR) добавляет `popularPages` и `exitPages`. **API-результат ещё не получен в текущей среде**. Старый приватный отчёт `/workspace/.cloud/magic-metal/analytics/report-28-days.json` не смонтирован на Windows-устройстве и нельзя объявлять его доступным. В среде Windows `YANDEX_METRIKA_TOKEN` в process env не найден. Прежний рабочий binding был в другом cloud runtime.

## Что означает «поведение клиентов»
- Просмотры и уникальные посетители по путям /produkciya/…; это интерес к разделам, но не обязательно к конкретным товарам.
- Время визита и глубина просмотра не равны времени на конкретной странице.
- «Выход с карточки» не означает доказанное недовольство: посетитель мог найти телефон/почту.
- Нужен сегмент `ym:s:isRobot = no`, иначе отчёт может ошибочно оптимизировать поведение роботов.
- Нужно сопоставить `catalog_product_opened`, `size_selected`, `request_click`, `request_started`, `request_sent` по сопоставимым визитам и затем агрегированные коммерческие стадии.

## Рекомендуемая система без усложнения
Еженедельно **анализировать** доступную Метрику и заявки, а не переснимать каталог: API read-only → очищенный отчёт по разделам, регионам, ботам и этапам → одно приоритетное ограничение → точечный PR → QA и оценка результата → закрепление или откат. Не добавлять PostHog/GrowthBook/OTel/RudderStack только потому, что они существуют.
