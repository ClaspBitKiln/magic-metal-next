# Восстановление подключения Obsidian через API

Найдены несколько этапов подключения Obsidian. Самый близкий к реальному подключению через API — связка **Obsidian Local REST API + MCP + туннель до компьютера ASUS-SAAS**. Эту схему прорабатывали в июле и сентябре 2026 года.

> **Важный статус:** есть подтверждения работоспособности локального API и отдельных проверок, но нет надёжного подтверждения, что ChatGPT смог полноценно читать и записывать заметки через весь внешний мост.

## 1. Архитектура

```text
ChatGPT Web
  └─ запросы к заметкам и поиск по памяти
      └─ MCP через HTTPS-туннель
          └─ ASUS-SAAS / tunnel-client
              └─ Obsidian Local REST API
                  └─ Vault: C:\Users\asus\Documents\inn-bot
```

Основная идея — работать с существующим хранилищем Obsidian напрямую, без копирования vault и без изменения проекта `inn-bot`. Изначально договорились начать с доступа только на чтение.

## 2. Сохранённые параметры

### Obsidian Local REST API

- Плагин с поддержкой MCP, версия **4.1.3**.
- Локальный MCP endpoint: `http://127.0.0.1:27123/mcp/`.
- Также проверялся HTTPS-вариант на порту `27124`.
- Авторизация: API-ключ в заголовке `Bearer`.
- Секретный ключ в этой заметке не хранить и не приводить.

### Туннель

- Имя: `Magic-Metal-Obsidian`.
- ID: `tunnel_6aa19edd8eb88191acc4d92b035cbd55`.
- Клиент: `tunnel-client v0.0.14`.
- Компьютер: `ASUS-SAAS`.

### Хранилище и заметка

- Vault: `C:\Users\asus\Documents\inn-bot`.
- Предполагавшаяся заметка: `Memory/Magic Metal/TRADE_AUTOMATION.md`.
- Скрипт автозапуска: `MAGIC_METAL_OBSIDIAN_MCP_AUTOSTART_FINAL.bat`.

## 4. План продолжения

Не строить подключение заново, пока не проверено состояние существующей конфигурации.

1. На ASUS-SAAS проверить, что Obsidian запущен и установлен нужный Local REST API/MCP-плагин.
2. Проверить наличие туннеля `Magic-Metal-Obsidian`, клиента `tunnel-client v0.0.14` и BAT-файла автозапуска.
3. Проверить локальный HTTP endpoint.
4. Отдельно проверить внешний MCP endpoint и авторизацию.
5. Выполнить реальный запрос чтения тестовой заметки через весь мост.
6. Только после успешного чтения отдельно согласовать и проверить запись заметки. Не включать запись по умолчанию.

### Локальная проверка HTTP-сервиса

В PowerShell на ASUS-SAAS:

```powershell
Invoke-WebRequest `
  -Uri "http://127.0.0.1:27123/" `
  -UseBasicParsing
```

Эта команда проверяет только локальный HTTP-сервис. Она **не подтверждает** работу MCP, внешнего туннеля или интеграции ChatGPT. Для защищённого MCP-запроса отдельно понадобится Bearer-ключ; не помещать его в репозиторий, заметки или логи.

## 5. Уточнение по предыдущим попыткам

В июле также рассматривался вариант через TRIGGERcmd и разрешённые команды. Сентябрьская конфигурация с Local REST API/MCP и туннелем была наиболее подробно зафиксирована.

## Правила безопасности и границы

- Не менять и не переносить vault `inn-bot`.
- Не сохранять в GitHub API-ключи, пароли, токены или содержимое документов с доступами.
- Не считать локальный HTTP 200 доказательством полной работы внешнего моста.
- Начинать с чтения; запись разрешать только после отдельной проверки.
- До фактического end-to-end теста статус подключения остаётся `partially_verified`.
