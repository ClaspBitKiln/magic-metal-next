## 2. Постоянные правила работы

- Цель: «Закупщику удобно». Короткий путь к параметрам и заявке; допустимы файл, неполные и нестандартные размеры, без обязательной корзины или регистрации. Целевые регионы: Сибирь, Дальний Восток, Север и СНГ; география клиента не определяет географию закупки.
- Сохранять вариант А и сравнивать реальный экран с оригиналом. Без оригинала visual_A=unverified; тесты не доказывают совпадение. Сохранять бренд, логотип, hero, раздел «Опыт» (#about), его цифры и клиентские логотипы, контакты и CTA «Отправить заявку» / «Позвонить».
- Каталог единый, арматура сохраняется. Новые разделы и товары требуют отдельного явного решения. Не выдумывать наличие, цены, фото, сертификаты, сроки и сочетания марка×форма×размер×ГОСТ.
- Покупатель не видит закупочные источники, поставщиков, закупочные цены, landed cost, маржу и внутренний ranking/score.
- Не смешивать DN и наружный диаметр, марку и сортамент. Ссылки — только на точные существующие страницы; неизвестное — текст. Марки остаются последней предусмотренной колонкой таблицы. Нормативный размерный ряд не означает наличие; применимость марки/ГОСТ к форме проверять по первичному документу.
- CMS/Neon/PostgreSQL/Payload, отдельное хранилище обращений, MATBOOK и новая CRM на паузе. Готовый код не удалять. P3 исключён. Старые планы не возобновляют эти работы.
- Действовать самостоятельно в согласованном охвате. Не запрашивать повторно уже данное разрешение. Новые принципиальные изменения отделять от обычных исправлений.
- Искать лучшее доступное решение по пользе, риску, времени и обратимости. Использовать ТРИЗ, примеры GitHub, подходящие skills, плагины и MCP. При доказанном отказе искать другой штатный способ; повторять запрос только после изменения условий. Найденный код проверять, не копировать слепо.
- Плагины/MCP выбирать под операцию и проверять реальный доступ. Использовать прежние привязки. Не обходить сеть, MFA или CAPTCHA. Название сервиса в истории не доказывает подключение.
- Агентам — разные участки и владение файлами. Основной агент объединяет результат. Без дублирования успешных тестов и одновременной правки одного файла. Не ослаблять проверки ради green: исправлять причину или доказанно устаревшее ожидание с сохранением смысла.
- Платные тарифы, новые внешние интеграции, смена DNS и маршрутизации уведомлений требуют отдельного решения; существующую почту не отключать.
- Критический визуальный контент доступен из исходного HTML без JS. Тяжёлые base64 не встраивать в первый ответ; не добавлять клиентский код ради оформления.
- Рыночный пример, норматив, подтверждённое предложение и складской остаток — разные доказательства. Не копировать чужие тексты, фото, цены и обещания.
- Реальные тестовые письма уже отправлялись: повторять только по новому основанию и отдельному явному запросу владельца. В QA блокировать POST, уведомления и аналитику. Наличие формы не доказывает доставку письма.
- Секреты не выводить и не переносить в чат/Git/документ. Уборка — по конкретному согласованному списку. Git и outbox не равны синхронизации Obsidian.

Актуальные правила: AGENTS.md, MEMORY.md и мастер-скилл сайта. Датированные ошибки, старые SHA и архивные шаблоны не являются действующими задачами.

### Два способа доступа

Подтверждённая рабочая история: ChatGPT → приложение Remote Desktop Commander → mcp.desktopcommander.app → подключённый Windows-клиент → файлы vault. Источник: docs/ai/PRODUCT_DOCUMENTATION_RELEASE_2026-11-03.md, коммит6acb4d2: запись и полное чтение 38-строчной заметки. Это основной путь; отдельный публичный REST-шлюз и Obsidian API-ключ для чтения файлов через Remote не обязательны.

- Через действующий Remote Desktop Commander: подключиться именно к Windows владельца, проверить имя ПК и vault, затем читать файлы заметок напрямую. Для этого пути отдельный REST API не требуется. Наличие облачного рабочего стола не означает подключение к этому ПК. В текущем наборе инструментов Remote Desktop Commander отсутствует.
- Через защищённый шлюз: облачный клиент → Cloudflare Access / аутентификация → named Cloudflare Tunnel → локальный Magic Metal Gateway 127.0.0.1:8787 → Obsidian Local REST API. Это сохранённая проектная схема, действующий публичный hostname не установлен. Не подставлять IP из другого раздела файла учётных данных. Broker не является OBSIDIAN_API_URL.

### Адреса и параметры

```sh
REST: https://127.0.0.1:27124
MCP:  https://127.0.0.1:27124/mcp/
HTTP loopback, только если включён: http://127.0.0.1:27123/mcp/
OBSIDIAN_API_URL=<проверенный HTTPS-адрес шлюза>
OBSIDIAN_API_KEY=<существующий Bearer-ключ, только защищённое хранение>
```

127.0.0.1 из облака означает облачную машину. Указанные порты Windows не доказывают удалённую доступность. TLS-проверку не отключать: сертификат локального плагина добавить через NODE_EXTRA_CA_CERTS; наружу публиковать шлюз с аутентификацией, не голый Obsidian.

### Проверка без потери заметок

- Проверить Windows, запущенный Obsidian, включённый Local REST API и реальный доступный endpoint. Сначала health/read/list/search; прочитать актуальные правила из vault.
- Для записи выбрать новую заметку или точечное дополнение, затем прочитать обратно и сверить содержимое/SHA256. Чужие правки не перезаписывать. До объявления шлюза готовым проверить отказ вне разрешённого vault/path и отказ разрушительных операций.
- scripts/sync_obsidian.mjs умеет создавать заметку через /vault/… и делать readback; при несовпадающем существующем тексте останавливается. Для одного чтения скрипт не запускать: возможен PUT.

Источники: docs/ai/OBSIDIAN_WINDOWS_BOOTSTRAP.md; OBSIDIAN_SYNC_ARCHITECTURE.md; OBSIDIAN_AUTOSYNC_OPERATIONS_2026-10-29.md. Там сохранены детали шлюза и история проверок; эти записи не подтверждают сегодняшнюю связь.
