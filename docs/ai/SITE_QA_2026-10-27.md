## Hero: устойчивость и скорость

При контролируемой остановке ответа после 20 400 байт цельный hero остаётся
недогруженным. Конечный вариант загружает 18/18 частей на 320/390/1536 px.
Это synthetic fault injection, не доказательство причины на каждом провайдере.

Локальные mobile Lighthouse 13.5.0 fixtures, два cold-profile запуска варианта:
до/после performance 100, CLS 0, TBT 0. LCP до 1,353–1,431 с, после 1,355–1,361 с:
достоверное ускорение не установлено. Мобильный трафик вырос на 18 336 байт;
крупнейший hero-ответ уменьшился с 32 148 до 3 404 байт. Запросов hero 18 вместо 1.
Исходный HTML gzip 12 995 → 12 839 байт; исходных скриптов 1 → 1.

Типографика hero до/после: h1 32 / 33,15 / 65,28 px на 320/390/1536; текст 17 px,
кнопки 16 px. Настоящий browser zoom 200% не проверен: headless extension не
запустилась. DPR/CSS zoom не выдавались за эту проверку. Прежний размер полей
формы 13 px может вызывать iOS autozoom; эта правка его не меняет.

## Публикация и границы доказательств

Коммит hero `3c945bd` отправлен в main. После этого живой `magicmet.ru` отдаёт
18 активных hero-полос; старого цельного изображения и inert template в HTML нет.
Нативный Chromium с проверкой TLS и предоставленным средой CA загрузил все 18
частей на 390/1536 px без JavaScript; desktop-скриншот показывает полную фотографию.
На mobile существующие кадрирование и белое наложение визуально скрывают большую
часть фотографии, хотя все файлы декодированы. Это не равно их сетевой недоступности.

Пользователь продолжал видеть верхнюю полосу в своём Chrome. Предложен отдельный
URL `https://magicmet.ru/?hero=3c945bd`; результат на его соединении ещё требует
подтверждения. Облачная проверка не подменяет проверку маршрута пользователя.

Общая пачка отправлена в main коммитом `f0b520f`. Живой CSS содержит исправленные
правила справочников. Повторная нативная проверка опубликованного сайта: оба
справочника на 320/820 px с раскрытыми группами без переполнения; отдельный URL
главной на 1536 px загружает 18/18 частей и показывает полную фотографию.
