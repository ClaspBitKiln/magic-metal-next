# Magic Metal — аудит и план сайта

Дата: 2026-09-14  
Статус: рабочий план; production не изменён.

## 1. Целевой продукт

Magic Metal развивается как одна система:

`сайт → RFQ → Parser → Product Identity → Supplier Discovery → Verification → Offers → Logistics → Split → Ranking → Margin/Risk → QA → Quote → DealResult → Knowledge Loop`.

Публичный сайт принимает заявку и документы. Внутренний RFQ Workbench помогает менеджеру выбрать доказанную закупочную возможность. Клиентская часть не показывает поставщика, источник, закупочную цену, landed cost, маржу, score или служебные комментарии.

## 4. Критические пробелы аудита

### P0 — точность Metalinfo

Опубликованный адаптер не реализует полностью правила из Obsidian:

- exact-match не проверяет стандарт/ГОСТ;
- дата публикации источника не отделена от `observedAt`;
- неизвестная freshness не имеет явного статуса;
- нельзя доказать, что локальные тесты Desktop реально соответствуют опубликованному коду;
- идентификатор на основе `Date.now()` затрудняет детерминированность;
- UI называет результаты «реальными вариантами», но должен явно показывать `observed / needs verification / stale`.

### P0 — ввод RFQ

Текущий UI использует зашитый пример заявки. Нужны пользовательский текст и серверная обработка TXT/CSV. Excel/PDF/Word/изображения допускаются только через отдельный extractor с проверяемым черновиком и ограничениями размера/типа.

### P0 — доказательность

Оффер допускается к ranking только при связи:

`категория + размер + стенка/толщина + марка + ГОСТ/ТУ + единица + evidence URL + дата источника`.

Benchmark, capability и observed offer не являются confirmed offer.

### P1 — эксплуатация

- неизвестно, настроены ли production-переменные Firecrawl/ATI;
- live-проверка Metalinfo не подтверждена;
- Payload API-тест требует `PAYLOAD_SECRET` и `DATABASE_URL`;
- общий TypeScript baseline требует отдельного разбора;
- публикация запрещена до полного QA gate.

## 5. География закупочного поиска

1. Урал: Екатеринбург, Челябинск, Магнитогорск, Первоуральск, Нижний Тагил.
2. Затем Москва/Московская область и европейская часть РФ.
3. Каждый источник оценивается для РФ и СНГ, включая Узбекистан.
4. Сравнивается полный landed cost, срок, наличие, документы и риск, а не минимальная цена.
5. Split-сценарий учитывает дополнительные рейсы, консолидацию, документы и ограничения количества.

## 6. План выполнения

### Этап A — восстановить проверенный RFQ Workbench

- создать рабочую ветку от `rfq-workbench-mvp`;
- восстановить строгий exact-match для размера, стенки, марки и ГОСТ;
- добавить единицу, НДС, количество, поставщика и стабильную дедупликацию;
- добавить `sourcePublishedAt`, `sourceUpdatedAt`, `observedAt` и явный freshness status;
- неизвестную/старую дату помечать `needs-verification` или `stale`, не `confirmed`;
- добавить профильные deterministic tests.

Критерий выхода: целевые тесты проходят; соседняя позиция, другой ГОСТ, другая единица, повтор URL и неизвестная дата не создают подтверждённый exact-offer.

### Этап B — нормальный ввод заявки

- заменить зашитую RFQ редактируемым вводом;
- добавить TXT/CSV;
- добавить серверные ограничения файлов;
- документы и изображения превращать только в проверяемый черновик;
- не хранить и не пересылать файл без явного рабочего сценария.

Критерий выхода: ввод и ошибки покрыты тестами; клиентские данные не попадают во внешние источники без необходимости.

### Этап C — один вертикальный RFQ по Уралу

На одной типовой позиции трубы:

`RFQ → Metalinfo → evidence → manager review → логистика Урала → landed cost → risk`.

Не отправлять КП клиенту. Не объявлять наличие подтверждённым без проверки поставщика.

### Этап D — сравнение Москва/Европейская РФ → Узбекистан

Для сопоставимой позиции сравнить уральский, московский/европейский и при необходимости split-маршрут. Зафиксировать погрузку, перевозку, консолидацию, срок, документы, неизвестные поля и risk allowance.

### Этап E — Payload и менеджерское решение

- сохранить RFQ и результаты поиска;
- связать выбранный менеджером вариант с черновиком Quote;
- записывать DealResult только после реального решения;
- использовать фактический результат сделки для Knowledge Loop.

### Этап F — новые источники

Подключать по одному адаптеру и только с тестами:

1. MC.ru;
2. официальные коммерческие каналы заводов;
3. металлоторги и склады;
4. специализированные источники.

E-Metall подключать только после получения официального endpoint, схемы ответа и способа авторизации.

### Этап G — production gate

Обязательно выполнить:

- `pnpm lint`;
- `pnpm test:int`;
- `pnpm test:e2e`;
- `pnpm qa:production`;
- `pnpm build`;
- проверку client boundary и секретов.

Если любой пункт не выполнен или среда недоступна — статус NOT READY.

## 7. Полезные правила, перенесённые из практики inn-bot

Код и файлы `inn-bot` не изменяются и не копируются. Для Magic Metal используются только проверенные рабочие принципы:

- один актуальный файл состояния проекта;
- перед изменениями сверять ветку, commit и remote;
- не считать локальную, GitHub и production-версию одинаковыми;
- handoff фиксирует context, branch, changed files, tests, blockers, next action и do-not-do;
- секреты остаются только в environment/secret management;
- перед push состояния сначала получить актуальную удалённую версию и проверить diff;
- маленькие изолированные изменения, тесты и только затем публикация;
- production-инциденты документируются отдельно.

## 8. Не делать

- не создавать новый сайт, CRM или параллельный каталог;
- не вливать старые ветки wholesale;
- не выдавать benchmark за оффер;
- не выдавать observed offer за подтверждённое наличие;
- не использовать LLM как доказательство цены, ГОСТ, наличия или логистического тарифа;
- не раскрывать внутреннюю закупочную экономику клиенту;
- не менять production до прохождения QA gate.

## 9. Следующее действие

Создать ветку от `rfq-workbench-mvp` и выполнить этап A: строгий Metalinfo contract + freshness + тесты. После зелёной проверки перейти к одному живому RFQ по Уралу.
